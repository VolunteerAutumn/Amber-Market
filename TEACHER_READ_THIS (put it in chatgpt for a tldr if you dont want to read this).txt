crud in amber market means create, read, update and delete, and we implemented all of it through the productscontroller and entity framework core. create happens when an admin adds a new product. the create get method loads the available categories and displays the form, while the create post method receives the product data and the uploaded image as an iformfile. we check that an image was selected and that the chosen category actually exists, then we generate the folder name from the category name and create the folder inside wwwroot/images/skins if it doesnt already exist. the image gets a random guid filename so two uploads cant accidentaly have the same name, then the actual file is saved to the folder. after that, the products imagepath is set to something like /images/skins/awp/8b7c....png, and entity framework saves the product info to postgresql. read is basically just getting info from the database. the index method gets all products and uses include to load their categories, while details searches for one specific product using its id. the admin products page also reads the products from the database and displays them in a table. razor then takes the data from the controller and generates the html, while the imagepath tells the browser where to find the actual image. update is handled by edit. the get method finds the existing product and loads its info into the edit form. the post method receives the changed product and optionally a new image. if no new image was selected, the old image stays where it is. if a new image was selected, we first delete the old physical image using deleteimage, then create the correct category folder, save the new image with a new guid filename, and update imagepath in the database. finaly, savechangesasync updates the product in postgresql. delete works by finding the product, deleting its physical image with deleteimage, removing the product from entity framework, and calling savechangesasync. so both the database record and its image disapear. categories work pretty similarly, but they also control the physical folders. when an admin creates a category, we save it to the database and then create a folder at wwwroot/images/skins/categoryname. the folder name is generated by converting the category name to lowercase, replacing invalid filename characters with underscores, and replacing spaces with underscores. for example, ak-47 skins could become ak-47_skins. when a category is renamed, we calculate the old and new folder names. if they are different, renamecategoryfolder uses directory.move to physicaly rename the folder, and then we update the imagepath of every product belonging to that category so the database points to the new folder. when a category is deleted, we first delete all the product images inside it, then delete the entire category folder recursively with directory.delete, and finaly remove the category from the database. because the product-category relationship uses cascade delete, the products belonging to that category are also deleted from postgresql. basicly, postgresql stores the product info and image path, while wwwroot/images/skins stores the actual image files. imagepath connects the two. if the database contains /images/skins/awp/abc123.png, the real file is wwwroot/images/skins/awp/abc123.png. so the whole thing works like this: the admin submits a form, the controller recieves the data, entity framework handles the database, the filesystem handles the actual images and folders, the database stores the images web path, and asp.net serves the image from wwwroot.
